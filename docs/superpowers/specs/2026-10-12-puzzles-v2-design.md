# Задачи v2: дизайн (этап 3, подпроект 1, вторая версия)

Дата: 2026-10-12. Статус: ждёт проверки учеником.

Основа: спецификация v1 `docs/superpowers/specs/2026-10-11-puzzles-design.md` и её реализация (не закоммичена). Решения ученика от 2026-10-12 записаны в памяти тренера (`stage3-plan-decisions`).

## Зачем

В v1 после первого неверного хода задача сразу заканчивается и показывает решение. Ученик хочет учиться как на Lichess: неверный ход опровергается на доске, он видит почему, и пробует ещё раз. Кроме того, задача должна принимать любой ход, который не хуже авторского, а не только ход из записанного решения.

Успех:

- Неверный ход: на доске появляется опровергающий ответ соперника, оценка, при необходимости стрелки и короткая надпись, почему ход плох. Кнопка «Ещё раз» возвращает позицию, ученик ищет дальше. Для повторения задача уже считается ошибкой.
- Верный ход: «Верно, продолжайте», соперник отвечает сам, задача в несколько ходов идёт шаг за шагом.
- Ход оценивается движком во время решения. Ход, который сохраняет тот же класс исхода и почти не уступает авторскому, засчитывается. Ход того же класса, но заметно слабее, - не ошибка: «Хороший ход, но есть сильнее». Ход, который роняет класс исхода (был мат - остался только выигрыш материала, был выигрыш - стало равно), - ошибка.
- Если у задачи есть второе равноценное решение, после решения ученику предлагается найти и его.
- Stockfish работает отдельным сервисом в Docker с HTTP API. К нему подключаются сервер доски и импорт задач, позже и другие потребители.
- Новые задачи берутся сначала из книг, Lichess идёт дополнением.
- «Радуга» переимпортирована по мягкому правилу: достаточно, чтобы первый ход выигрывал. В базе больше 1037 задач из «Радуги».

## Что сказал ученик и что допущено

Сказано (2026-10-12): движок - отдельный Docker-сервис с API; неверный ход показывает опровержение, оценку, стрелки и описание, затем откат и повторная попытка, в повторении задача считается ошибкой; классы ходов относительно исхода, а не по разнице в пунктах; равноценные ходы засчитываются с предложением найти второе решение; ходы оцениваются во время решения; задачи из книг в приоритете над Lichess; «Радугу» переимпортировать с правилом «первый ход выигрывает».

Допущено тренером: всё из раздела «Решения без ученика» в конце. Каждое решение там можно отменить при проверке спецификации.

## Сервис движка

### Что это

Новый пакет `web/packages/engine` (TypeScript, Nest, как сервер доски) и новый сервис `engine` в `docker-compose.yml`. Внутри - Stockfish и пул UCI-процессов. Обёртка UCI переезжает сюда из `web/packages/puzzles/src/engine/uci.ts` вместе с тестами.

Stockfish собирается из исходников в многоэтапном `Dockerfile` по тегу той версии, что стоит на хосте (сейчас Stockfish 19), с сетью NNUE этой версии. Архитектура сборки выбирается по платформе образа (`arm64` - сборка под Apple Silicon, `amd64` - `x86-64-avx2`). Точные имена тега и целей `make` проверяются в плане по репозиторию Stockfish: это внешний источник, он может отличаться от того, что написано здесь.

Порт 8766. Наружу он открыт только на `127.0.0.1`, чтобы импорт на хосте мог к нему обращаться. Сервер доски ходит к нему по сети Docker (`ENGINE_URL=http://engine:8766`).

### Детерминизм

Каждый процесс пула работает с `Threads=1`. Перед каждым анализом идёт `ucinewgame`, поиск ограничен числом узлов. Так одна и та же позиция с теми же параметрами всегда даёт одну и ту же оценку, на любой загрузке машины. Это закрывает разброс вердиктов «единственный ход» около порога, который был в v1 (см. журнал v1). Параллельность даёт число процессов в пуле, а не потоки внутри одного процесса.

### API

`POST /analyse`

```
запрос:  { fen: string,
           multipv?: 1..5,              // по умолчанию 1
           searchmoves?: string[],      // UCI, только эти ходы
           nodes?: number,              // по умолчанию ENGINE_NODES, не больше 5 000 000
           priority?: "interactive" | "batch" }   // по умолчанию interactive
ответ:   { fen, nodes, lines: [{ move, cp?, mate?, pv: string[], depth }] }
```

Оценки даны со стороны того, кто ходит в `fen`, как в нынешнем `EngineLine`. Неверный FEN или нелегальный ход в `searchmoves` - ответ 400 с понятным текстом. Позиция, где уже мат или пат, - ответ 200 с пустым `lines`.

`GET /health` - `{ ok, version, workers, busy, queued }`. Это и healthcheck для Docker.

Очередь общая на пул, с двумя приоритетами: запросы `interactive` (ход ученика) обгоняют `batch` (импорт). Переполнение очереди (больше 1000 запросов) - ответ 503.

Настройки через переменные окружения: `ENGINE_WORKERS` (по умолчанию 4), `ENGINE_HASH_MB` (64 на процесс), `ENGINE_NODES` (1 000 000).

### Клиент

`EngineClient` на `fetch` с тем же интерфейсом `analyse(fen, opts)`, что у нынешнего `Engine`. Лежит в `@board/shared`, чтобы его брали и сервер доски, и импорт. Таймаут запроса и понятная ошибка «engine unavailable at <url>» при недоступном сервисе.

### Кто подключается

- Сервер доски: оценка ходов в задачах.
- Импорт задач (`@board/puzzles`): вместо своего процесса Stockfish ходит в сервис с `priority: "batch"`. Импорт «Радуги» отправляет столько запросов одновременно, сколько процессов в пуле. Перед началом импорт проверяет `/health` и без сервиса завершается с ошибкой «запустите docker compose up -d engine».
- `coach` на Python не меняется: `analyze` и `review` работают с локальным Stockfish до этапа 4, когда `coach` переносится на TypeScript и тоже переходит на сервис. Это записывается в ROADMAP.

## Оценка хода во время решения

### Классы исхода

Класс исхода считается по оценке движка со стороны решающего, по модели win% Lichess, которая уже есть в коде (`winPct`):

| Класс | Условие |
|---|---|
| мат | движок видит форсированный мат решающего |
| выигрыш | win% не меньше 75 (около +3) |
| перевес | win% от 60 до 75 (от +1.1 до +3) |
| равно | win% от 40 до 60 |
| хуже | win% меньше 40 |

### Вердикт по ходу ученика

Позиция, где ходит решающий, называется узлом. В каждом узле есть ожидаемый ход: ход из решения, пока ученик идёт по записанной линии, или лучший ход движка, если ученик раньше свернул на равноценную альтернативу.

1. Ход совпал с ожидаемым - **верно**, движок не нужен, ответ мгновенный.
2. Ход дал мат - **верно**, задача решена.
3. Иначе ход оценивается движком и сравнивается с ожидаемым ходом в этом узле:
   - класс исхода ниже, чем у ожидаемого хода, - **ошибка**;
   - класс тот же, а win% уступает меньше чем на 5 пунктов (порог неточности из `coach.toml`) - **равноценно**, засчитывается как верный ход. Для мата «равноценно» значит мат не длиннее ожидаемого;
   - класс тот же, а уступает 5 пунктов и больше (для мата - мат длиннее) - **хороший, но слабее**. Это не ошибка.
   - ход сильнее ожидаемого (выше класс или больше win%) - тоже **равноценно**. Такой случай пишется в историю попытки, чтобы тренер посмотрел, не ошибается ли решение.
4. Позиция после хода ученика с патом, недостатком материала или повторением оценивается как равная (win% 50).

Пример: в задаче мат в 2, ученик нашёл ход, после которого движок видит мат в 3, - «хороший, но слабее», ученик ищет дальше. Ученик выиграл ферзя вместо мата - ошибка. В задаче на выигрыш фигуры ученик выиграл ту же фигуру другим ходом с той же оценкой - засчитано.

### Где считается и сколько стоит

Когда ученик попадает в новый узел, сервер доски заранее запрашивает анализ узла с `multipv 3`. Отсюда берутся оценка ожидаемого хода и ближайшие альтернативы. Если ожидаемого хода среди трёх нет (решение книги слабее лучших ходов движка), он оценивается отдельным запросом с `searchmoves`. Если ход ученика есть среди трёх, вердикт готов без нового запроса. Если нет, идёт один запрос с `searchmoves` этого хода. Ответ этого запроса содержит и опровержение: второй ход его линии - лучший ответ соперника.

Ход ученика сразу встаёт на доску, плашка показывает «Проверяю ход…», фигуры заблокированы. Вердикт применяется вторым изменением состояния, когда пришёл ответ движка. Пока идёт проверка, очередь изменений доски не блокируется: команды тренера проходят. Вердикт применяется только к той же задаче и тому же узлу, как сейчас ответ соперника (`puzzleReply`).

В памяти сервера доски хранится кэш анализов по ключу «FEN + параметры», последние 500 записей. Повторная задача в тот же день не ждёт движок.

### Движок недоступен

Ход из решения и мат засчитываются без движка, как в v1. Любой другой ход откатывается с надписью «Не могу проверить ход: движок недоступен». Попытка при этом не засчитывается ни как верная, ни как ошибка. Сервер доски пишет в лог одну строку на каждую неудачу.

## Как это выглядит на доске

### Верный ход

Плашка «Верно, продолжайте». Через 0,5 секунды соперник отвечает: ходом из решения или, после равноценной альтернативы, лучшим ходом движка. Последний ход решения - «Решено: <задача>».

Задача, где ученик ушёл на равноценную альтернативу, кончается так: мат, или ученик сделал столько же своих ходов, сколько в записанном решении, и класс исхода не упал.

### Неверный ход

1. Ход ученика стоит на доске, следом идёт ответ соперника из линии движка.
2. Красная стрелка показывает этот ответ. Если ответ тихий (не взятие и не шах), синяя стрелка показывает следующий ход соперника из той же линии: это то, чем он грозит.
3. Плашка красная, в ней короткое описание и оценка со стороны ученика. Описание собирается по шаблонам из данных движка, без пересказа линии:
   - «После Rxd8 вам мат в 3.» - если движок видит мат против решающего;
   - «Мат упущен. После Rxd8 оценка +1.2 (перевес).» - если в узле был мат, а после хода его нет;
   - «После Rxd8 вы теряете фигуру. Оценка −2.8 (хуже), было +4.1 (выигрыш).» - в остальных случаях. Потеря материала называется, если за четыре полухода линии движка баланс решающего упал хотя бы на пешку: пешка, две пешки, фигура, ладья, ферзь, иначе «N пешек».
4. Кнопка «Ещё раз» возвращает курсор в узел перед неверным ходом и снимает стрелки. Неверный ход и опровержение остаются в дереве веткой ученика: тренер видит их в `coach board state`.
5. В повторении по FSRS задача уже ошибка. Попытка пишется в историю сразу при первой ошибке, поэтому брошенная после ошибки задача тоже считается нерешённой. Дальнейшие ошибки в той же попытке историю не меняют.

Подробнее тренер объясняет в чате: он читает `coach board state`, где видны ветка ученика и текст плашки.

### Хороший, но слабее

Ход ученика стоит на доске, соперник не отвечает. Плашка жёлтая: «Хороший ход, но есть сильнее. Оценка +3.4, лучший ход даёт мат в 2» (лучший ход не называется). Кнопка «Ещё раз» как при ошибке. Это не ошибка, но оценка FSRS у такой попытки не выше `Hard`.

### Сдаться

Кнопка «Показать решение» видна всё время решения. Она доигрывает решение от текущего узла главной линией, ставит курсор в узел и рисует зелёную стрелку решения. Если ошибок до этого не было, попытка пишется как ошибка.

### Второе решение

Анализ корня (`multipv 3`), который сервер запрашивает при старте задачи, показывает, есть ли другие равноценные первые ходы. После решения, если такой ход есть и ученик его ещё не играл, плашка говорит «Решено! Есть ещё одно решение» и показывает кнопку «Найти другое». Она возвращает позицию задачи в режим решения. Уже найденный первый ход в этом заходе отвечает «Это решение вы уже нашли». Второй заход в повторение не пишется.

Классификация задачи (одно решение, несколько равноценных, главное плюс более слабые) хранится в сессии задачи и видна тренеру в `coach board state`, но ученику до решения не показывается.

### После задачи

Как в v1: режим становится `free`, ученик листает дерево и пробует свои ходы.

## Оценка для FSRS

| Итог попытки | Оценка |
|---|---|
| ошибка или «Показать решение» | `Again` |
| решено, но был ход «слабее» или дольше 60 секунд | `Hard` |
| решено чисто | `Good` |

Запись в истории получает поля `weaker` (число ходов «слабее») и `altBetter` (ученик сыграл ход сильнее записанного решения), чтобы тренер видел это в `coach puzzles stats`.

## Выбор задачи

Порядок в `next` остаётся: сначала карточки с наступившим `due`, потом новые задачи. Меняется выбор новой задачи:

1. Книги: Полгар и «Радуга» по очереди, первой идёт та, где у ученика меньше попыток. Внутри книги задачи идут по номерам, как сейчас.
2. Lichess, только если в книгах нет новых задач нужных тем.
3. `--source lichess` по-прежнему даёт задачу Lichess сразу.

## Переимпорт «Радуги»

Сканы уже распознаны (`data/books/raduga-diagrams.json`), заново считается только решение.

Мягкое правило для книжных позиций без ответа книги: лучший первый ход по движку должен давать класс исхода «выигрыш» или «мат». Уникальность первого хода больше не требуется: равноценные альтернативы теперь засчитываются при решении. Позиция, где лучший ход даёт только «перевес» или меньше, отбрасывается с причиной «первый ход не выигрывает».

Линия решения строится так: решающий играет лучший ход движка, соперник - лучший ответ. Линия заканчивается:

- матом;
- когда материал реально выигран: после хода решающего и лучшего ответа соперника баланс решающего вырос хотя бы на 2 пешки по сравнению с исходной позицией (тогда линия кончается ходом решающего, ответ отбрасывается);
- после 8 ходов решающего.

Стоп-правило v1 («оценка после хода не меньше +3») для «Радуги» не годится: после первого хода комбинации движок уже видит выигрыш, и решение обрезалось до одного хода.

Id задач не меняются (`raduga:<том>-<часть>-<номер>`), поэтому карточки FSRS сохраняются. Полгар не переимпортируется: у неё ответы из книги и строгая проверка движком остаются как в v1. Lichess не меняется.

Ожидание: из 344 позиций с «неединственным первым ходом» большая часть проходит. Число отчёт показывает, ориентира в процентах нет.

## Изменения по компонентам

- `web/packages/engine` (новый): сервис, пул, очередь с приоритетами, обёртка UCI, `Dockerfile` со сборкой Stockfish.
- `web/packages/shared`: типы API движка, `EngineClient`, новые поля сессии задачи (вердикт и текст плашки, ожидаемый ход, ошибки, найденные первые ходы, классификация), новые сообщения WebSocket `puzzleRetry`, `puzzleGiveUp`, `puzzleAnother`.
- `web/packages/server`: модуль оценки хода (чистые функции: класс исхода, вердикт, описание, баланс материала) и асинхронная проверка хода в `BoardService`; кэш анализов; новый выбор новой задачи; запись истории при первой ошибке.
- `web/packages/client`: плашки «Проверяю ход…», «Верно, продолжайте», «Хороший ход, но есть сильнее», ошибка с описанием, «Решено! Есть ещё одно решение»; кнопки «Ещё раз», «Показать решение», «Найти другое»; блокировка фигур на время проверки и после ошибки до «Ещё раз».
- `web/packages/puzzles`: импорт через `EngineClient`, мягкое правило и новое стоп-правило для «Радуги», параллельные запросы.
- `docker-compose.yml`: сервис `engine` с healthcheck; `board` зависит от него, но запускается и без него.
- `coach` (Python): `coach board state` печатает строку о задаче (статус, текст плашки, число ошибок). Остальное без изменений.
- Документы: `CLAUDE.md` (как идёт решение и что тренер читает в `state`), `SETUP.md` (сервис движка, переимпорт «Радуги»), `ROADMAP.md`.

## Ошибки

- Сервис движка: неверный FEN или ход - 400; переполнение очереди - 503; зависший процесс Stockfish убивается по таймауту и перезапускается, запрос получает 500, пул продолжает работу.
- Сервер доски без движка: см. «Движок недоступен».
- Импорт без движка: падает до начала работы с подсказкой, как запустить сервис.
- Ответ движка пришёл, а задача на доске уже другая или ученик ушёл из узла: вердикт отбрасывается.
- Перезапуск сервера доски во время проверки: при загрузке состояния незаконченная проверка запускается заново.

## Тесты

- Сервис движка: очередь и приоритеты, перезапуск упавшего процесса, 400 и 503 - на фейковом UCI-процессе; одна проверка на настоящем Stockfish в контейнере (мат в 1 находится, оценка детерминирована на двух запросах подряд).
- Оценка хода: чистые функции на заданных линиях движка - все пять классов, границы порогов, мат короче и длиннее, ход сильнее решения, пат, описание и баланс материала.
- Сервер доски e2e с фейковым клиентом движка: верный ход, ошибка с опровержением и «Ещё раз», «слабее», равноценная альтернатива с продолжением по движку, сдача, второе решение, движок недоступен, ответ движка после смены задачи, перезапуск во время проверки, запись истории ровно один раз.
- Выбор задачи: книги раньше Lichess, Lichess при пустых книгах, `--source lichess`.
- Импорт «Радуги»: мягкое правило и стоп-правило на фейковом движке (комбинация с жертвой даёт линию длиннее одного хода).
- Клиент: плашки и кнопки по состоянию, блокировка фигур.
- `coach board state` со строкой задачи через фейковый сервер.

## Приёмка

Во встроенном браузере Claude Desktop, тренер решает сам:

1. `docker compose up -d` поднимает `mongo`, `engine`, `board`; `GET /health` движка отвечает, версия совпадает с хостом.
2. Задача в несколько ходов: на каждом верном ходе «Верно, продолжайте», ответы соперника идут сами, в конце «Решено».
3. Неверный ход: на доске опровержение и стрелка, в плашке описание и оценка, «Ещё раз» возвращает позицию, затем задача решается; `coach puzzles stats` показывает её как ошибку.
4. Ход «слабее» в задаче на мат (мат длиннее) даёт жёлтую плашку и не считается ошибкой.
5. Ход, роняющий класс (выигрыш материала вместо мата), - ошибка.
6. Задача с двумя равноценными первыми ходами: второй ход засчитан, после решения предложено «Найти другое», второе решение находится.
7. `coach puzzles next` с темами по умолчанию даёт задачу из книги.
8. Отчёт переимпорта «Радуги»: число задач в базе больше 1037, 10 случайных новых задач решаются на доске и выглядят как задачи (первый ход выигрывает, линия не обрезана после первого хода).
9. Остановленный сервис движка: ход не из решения откатывается с надписью «движок недоступен», ход из решения проходит.

После приёмки - финальное ревью всей ветки (v1 и v2 вместе).

## Решения без ученика

Принятые тренером при написании спецификации. Любое можно поменять при проверке.

1. Пороги классов исхода: 75 / 60 / 40 win% (около +3 / +1.1 / 0), порог «равноценно» - 5 пунктов win% (неточность из `coach.toml`). Цена ошибки: спорные ходы у границы класса; пороги меняются в одном месте.
2. Возврат после ошибки и после хода «слабее» - по кнопке «Ещё раз», а не автоматически: ученику нужно время посмотреть опровержение.
3. Попытка с ошибкой пишется в историю сразу при первой ошибке, а не в конце.
4. Ход «слабее» ограничивает оценку FSRS до `Hard`.
5. Нужна кнопка «Показать решение»: без неё ученик, который не нашёл ход, застревает.
6. Детерминизм движка: один поток на процесс, `ucinewgame` перед каждым анализом, параллельность пулом. Цена: один анализ медленнее, чем на 6 потоках.
7. Импорт задач тоже ходит в сервис движка, своя обёртка UCI у него убирается.
8. Книги идут раньше Lichess целиком, Lichess - только когда книги нужных тем кончились, без доли «каждая пятая из Lichess». С темами по умолчанию это значит, что задачи Lichess появятся нескоро.
9. Стоп-правило линии «Радуги» по реально выигранному материалу (2 пешки и больше), а не по оценке.
10. Полгар не переимпортируется, её строгая проверка остаётся.
11. Описание неверного хода - по шаблонам из данных движка; объяснение идеи остаётся тренеру в чате.
12. Кэш анализов - в памяти сервера доски (500 записей), без коллекции в Mongo.
13. `coach` на Python до этапа 4 остаётся на локальном Stockfish.
