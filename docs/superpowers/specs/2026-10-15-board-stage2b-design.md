## Зачем

Сейчас тренер узнаёт о ходах ученика на доске, только если ученик сам скажет «попробовал вариант», а тренер прочитает `coach board state`. Ученик хочет писать о своих мыслях, а тренер должен уже видеть, что именно он сыграл. Кроме того, тренеру нужна панель рядом с доской, чтобы показывать оценку и линии движка, когда это уместно, и не показывать их, когда ученик думает сам.

Успех:

- Ученик делает ходы на доске в свободном режиме, пишет сообщение, и в контексте тренера уже есть эти ходы в SAN с номерами, без отдельной команды.
- Итоги задач (решено, ошибка, ход «слабее», «Показать решение») приходят тренеру тем же путём.
- Тренер включает на доске шкалу оценки, линии движка (от 1 до 3) и заметку. Без команды тренера ничего из этого не видно. Новая позиция или задача всё выключает.
- Закрыты хвосты ревью 2а: Origin у WebSocket, проверка тел HTTP-запросов, обрезка вариантов PGN по `--upto`, healthcheck сервиса `board`, ручная проверка превращения пешки.

## 1. Очередь событий ученика

### Какие события пишутся

Сервер доски пишет событие, когда ученик что-то сделал. Действия тренера (HTTP API, `coach ...`) событий не создают.

| Вид | Когда | Что сохраняется |
|---|---|---|
| `line` | ход ученика в свободном режиме | позиция, от которой начата ветка, ходы в SAN с номерами, id узлов |
| `delete` | ученик удалил ветку | первый ход удалённой ветки в SAN с номером, сколько полуходов удалено |
| `puzzle` | в режиме задачи: ошибка, ход «слабее», решено, «Показать решение» | id и подпись задачи, итог, ход ученика в SAN, текст плашки |

Листание (`navigate`) событием не считается: иначе каждое нажатие стрелки давало бы запись. Где ученик стоит сейчас, тренер узнаёт из строки «курсор» в выводе (см. ниже). Ходы внутри задачи отдельно не пишутся, их покрывают события `puzzle`. Шаг «Верно, продолжайте» тоже не пишется, пишется только итог.

### Склейка ходов

Подряд идущие ходы ученика склеиваются в одно событие `line`. Новый ход дописывается в последнее событие, если выполнены все условия:

- последнее событие очереди - `line` и оно ещё не прочитано;
- новый ход сделан из последнего узла этой ветки;
- дерево не заменялось с тех пор (номер замены дерева, `treeEpoch`, тот же).

Иначе начинается новое событие. Ход, который уже есть в дереве (ученик повторил существующий ход, сервер только передвинул курсор), тоже пишется: тренеру важно, что ученик выбрал этот ход.

### Хранение

Коллекция Mongo `inbox` в той же базе, что доска:

```
{ _id: number,            // возрастающий номер события
  at: Date,
  kind: 'line' | 'delete' | 'puzzle',
  treeEpoch: number,
  read: boolean,
  text: string,           // готовая строка для тренера, по-русски
  // line:   fromNode, nodes: NodeId[], sans: string[]
  // delete: node, san, plies
  // puzzle: puzzleId, label, result: 'wrong'|'weaker'|'solved'|'gaveUp', san?, banner? }
```

Текст события собирается в момент записи, потому что после замены дерева узлов уже не будет. Пример строк:

- `ветка ученика от 23...Nf5: 24.Nh6+ Kh8 25.Qf3 (узлы n57-n59)`
- `ученик удалил ветку 24.Nh6+ (3 полухода)`
- `задача polgar:0310: ошибка, ход Qg6+, «Мат упущен. После Qg6+ оценка +2.0 (перевес).»`

Номер замены дерева `treeEpoch` хранится в документе доски и растёт при каждой замене дерева (`PUT /api/board`, новая задача). Хранится не больше 500 последних событий, старые удаляются при записи.

### API

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/inbox` | непрочитанные события по возрастанию номера (не больше 50) плюс `more` - сколько ещё непрочитанных, и `cursor` - строка о курсоре |
| `POST` | `/api/inbox/ack` | `{ upto: number }`: пометить прочитанными все события с номером до `upto` включительно |

Строка `cursor` описывает текущее положение: ход, после которого стоит курсор, в SAN с номером, автор узла (партия, тренер, ученик), режим доски. Пример: `курсор после 24...Kh8 (ветка ученика), режим free`. Если на доске задача, строка говорит об этом: `на доске задача polgar:0310, решается`.

### `coach inbox`

```
coach inbox [--peek] [--hook]
```

- Без флагов: печатает непрочитанные события, затем строку курсора, затем помечает напечатанное прочитанным (`ack` с номером последнего напечатанного). Если событий нет, печатает «Новых действий ученика нет» и строку курсора.
- `--peek`: то же, но без пометки.
- `--hook`: режим для хука. Если событий нет, сервер не отвечает или случилась любая ошибка, ничего не печатает и выходит с кодом 0. Если события есть, печатает их с заголовком «Действия ученика на доске с прошлого сообщения:» и строкой курсора, затем помечает прочитанными. Таймаут запроса 2 секунды.

### Хук Claude Code

В `.claude/settings.json` проекта добавляется хук `UserPromptSubmit`, который вызывает `uv run --quiet coach inbox --hook` с таймаутом 10 секунд. По документации Claude Code вывод хука `UserPromptSubmit` в stdout с кодом 0 добавляется в контекст как дополнение к сообщению. Как это работает в приложении Claude Desktop (вкладка Code), проверяется при приёмке: это внешнее поведение, и оно могло измениться.

Хук выбран ещё в спецификации 2а, а не автопробуждение тренера: ученик сначала пишет, о чём думал, и тренер не отвечает на полуслове. В сессиях по коду хук ничего не печатает, пока на доске нет новых действий ученика.

`coach board state` очередь не трогает: он показывает дерево, а очередь отвечает на вопрос «что нового».

## 2. Панель рядом с доской

### Что на панели

- **Шкала оценки.** Вертикальная полоса у края доски, белые со стороны белых фигур (учитывает переворот доски). Над ней число со стороны белых, как на Lichess: `+1.2`, `−0.4`, `#3`, `#−2`.
- **Линии движка.** От 1 до 3 линий. В каждой оценка и первые 8 полуходов в SAN с номерами. Клик по линии ничего не делает: это показ, а не дерево (вариант на доску тренер ставит через `coach board line`).
- **Заметка тренера.** Простой текст до 2000 символов, переносы строк сохраняются, без разметки.

Панель занимает место в правой колонке над списком ходов. Если ничего не включено, панели нет совсем.

### Управление

Настройки хранятся в документе доски:

```
panel: { eval: boolean, lines: 0 | 1 | 2 | 3, note?: string }
```

| Команда | HTTP | Что делает |
|---|---|---|
| `coach board panel [--eval on\|off] [--lines N]` | `PATCH /api/board/panel` `{ eval?, lines? }` | включить или выключить шкалу и линии |
| `coach board note "текст"` | `PATCH /api/board/panel` `{ note }` | поставить заметку |
| `coach board note --clear` | `PATCH /api/board/panel` `{ note: null }` | убрать заметку |

`coach board state` печатает строку `panel eval=on lines=2 note="..."` (заметка обрезается до 60 символов), если что-то включено.

### Защита от подсказок

- Любая замена дерева (`PUT /api/board`, то есть `board load` и `show`, и старт задачи) выключает шкалу и линии и стирает заметку.
- В режиме задачи панель не показывается и анализ не запрашивается, даже если настройки включены.
- Включить панель может только тренер через HTTP. По WebSocket настройки панели не меняются.

### Анализ

Анализ считает сервис движка через `AnalysisService` сервера доски, который уже есть для задач: тот же кэш, склейка одинаковых запросов, приоритет `interactive`, бюджет узлов по умолчанию сервиса. `multipv` равен числу линий, но не меньше 1, когда включена только шкала.

Анализ запрашивается для узла под курсором, когда:

- панель включили или изменили число линий;
- курсор сдвинулся (ход, листание, `goto`) и панель включена.

Сдвиги курсора чаще одного раза в 300 мс склеиваются: анализ идёт для последнего положения. Если ответ пришёл для узла, на котором курсора уже нет, он не рассылается.

Результат идёт в браузер отдельным сообщением WebSocket и в Mongo не пишется:

```
{ event: 'analysis', data: {
    nodeId, fen,
    status: 'pending' | 'ready' | 'unavailable',
    lines: [{ cp?: number, mate?: number, san: string[] }]   // оценки со стороны белых
} }
```

Сначала сервер шлёт `pending`, затем `ready` или `unavailable`. При подключении новой вкладки и включённой панели сервер шлёт последний анализ (или запускает его). Перевод в SAN и в оценку со стороны белых делает сервер. Если позиция мат или пат, `ready` с пустым `lines`, и панель пишет «мат» или «пат».

Если движок недоступен, панель пишет «Движок недоступен», шкала серая, доска работает как обычно.

## 3. Хвосты ревью 2а

### Origin у WebSocket

Подключение к `/ws` из браузера с чужим `Origin` отклоняется на этапе рукопожатия (ответ 403). Разрешены `http://127.0.0.1:8765`, `http://localhost:8765` и адреса Vite для разработки `http://127.0.0.1:5173`, `http://localhost:5173`. Список меняется переменной `BOARD_ORIGINS` (через запятую). Подключение без `Origin` разрешено: браузер его всегда шлёт, а без него подключаются локальные клиенты (тесты, скрипты приёмки), и сервер слушает только `127.0.0.1`.

### Проверка тел HTTP-запросов

Валидаторы пишутся руками в `@board/shared`, без новой библиотеки, и применяются в контроллерах до вызова сервиса. Неверное тело - ответ 400 с кодом `bad_request` и понятным текстом, что именно не так.

| Тело | Проверки |
|---|---|
| `ReplaceBody` | ровно одно из `pgn` (строка) и `fen` (строка) или ни одного; `moves` - массив строк; `cursorPly`, `upto` - целые ≥ 1; `plyOffset` - целое ≥ 0; `orientation` - `white` или `black`; `title`, `gameId` - строки до 200 символов |
| `AddLineBody` | `at` - целое ≥ 0 или строка id узла; `moves` - непустой массив строк; `caption` - строка до 500 символов |
| `CursorBody` | `at` как выше; `arrows` - массив до 20 элементов, у каждого `from` и `to` - поле доски (`a1`-`h8`), `color` - `green`, `red` или `blue`; `caption` как выше |
| `ModeBody` | `mode` - `frozen` или `free` |
| `PanelBody` | `eval` - логическое; `lines` - целое 0-3; `note` - строка до 2000 символов или `null`; хотя бы одно поле |
| `PuzzleNextBody` | `id`, `theme`, `source` - строки (`source` из списка источников); `themes` - массив строк; `rating` - целое |
| `InboxAckBody` | `upto` - целое ≥ 0 |

Лишние поля игнорируются. Сообщения WebSocket от браузера уже проверяются в сервисе (неверный узел даёт `not_found`), их не трогаем.

### Обрезка вариантов PGN по `--upto`

Сейчас `--upto` обрезает только главную линию. Вариант из PGN, начатый до полухода N, переносится целиком и может показать продолжение партии. Исправление: при `upto` в дерево не попадает ни один узел с номером полухода ≥ N, ни в главной линии, ни в вариантах.

### Healthcheck сервиса `board`

В `docker-compose.yml` у `board` появляется healthcheck на `/api/health` (в образе `node:alpine` есть `wget` из busybox), с теми же интервалами, что у `engine`.

### Превращение пешки

Проверяется руками при приёмке во встроенном браузере: перетаскивание пешки на последнюю горизонталь, выбор фигуры, ход в дереве и в `coach inbox`.

## Ошибки и крайние случаи

- Mongo недоступна при записи события: ход ученика всё равно применяется, событие теряется, в лог сервера пишется одна строка. Очередь не должна ломать доску.
- Ученик сыграл ход, потом тренер заменил доску до прочтения: событие остаётся в очереди с текстом, собранным при записи, а id узлов в нём уже не существуют. Это нормально, текст самодостаточен.
- Две вкладки доски: события пишутся по факту хода, вкладки не важны.
- `coach inbox` и хук прочитали одни и те же события одновременно: `ack` идемпотентен, в худшем случае события покажутся дважды.
- Панель включена, курсор быстро листают: в движок уходит только последний узел, остальные склеиваются задержкой.
- Движок отвечает дольше, чем курсор стоит на месте: устаревший ответ не рассылается, но остаётся в кэше.

## Тестирование

- **Модульные, сервер.** Сборка текста событий (`line` с ходом белых и чёрных, с ненулевым `plyOffset`, `delete`, `puzzle` всех итогов); склейка (подряд, после другого события, после замены дерева, после прочтения); обрезка вариантов по `upto`; валидаторы на каждое поле из таблицы; перевод линии в SAN и оценку со стороны белых.
- **E2E, сервер.** Ход по WebSocket появляется в `GET /api/inbox`, `ack` его убирает; ходы склеиваются; удаление ветки и итог задачи пишутся; действия тренера не пишутся; включение панели даёт `pending`, затем `ready` (с поддельным движком), быстрые сдвиги курсора дают один анализ; движок выключен - `unavailable`; замена дерева выключает панель; в режиме задачи `analysis` не приходит; подключение с чужим `Origin` отклонено, со своим и без `Origin` принято; неверные тела дают 400.
- **Клиент.** Панель не рисуется, когда выключена и когда на доске задача; шкала учитывает переворот; линии и заметка отображаются; `unavailable` даёт надпись.
- **pytest.** `coach inbox` печатает и помечает прочитанным, `--peek` не помечает, `--hook` молчит без событий и без сервера; `board panel` и `board note` шлют нужные тела; `board state` печатает строку `panel`.

## Приёмка

Во встроенном браузере Claude Desktop и в терминале, сервисы в Docker:

1. Свободный режим, ученик делает три хода подряд на доске. `coach inbox` печатает одну строку ветки с номерами ходов и строку курсора, повторный вызов говорит «Новых действий ученика нет».
2. Хук: после ходов на доске следующее сообщение ученика приходит в контекст тренера вместе с блоком «Действия ученика на доске...». Проверяется в этом же приложении. Если хук в Claude Desktop не срабатывает, это записывается, и тренер на занятиях вызывает `coach inbox` сам.
3. Задача: ошибка, затем решение. В `coach inbox` два события `puzzle`.
4. `coach board panel --eval on --lines 2`: шкала и две линии под курсором, при листании обновляются. `coach board note "..."`: заметка видна.
5. `coach board load --game ... --ply N --upto N`: панель пропала, варианты PGN после N не видны.
6. `coach puzzles next`: панели нет. Выход из задачи и включение панели снова её показывают.
7. Движок остановлен: панель пишет «Движок недоступен», ходы на доске работают. Движок снова запущен.
8. WebSocket с `Origin: http://evil.example` отклонён (скриптом).
9. Превращение пешки перетаскиванием мышью: появляется выбор фигуры, ход в дереве и в `coach inbox`.
10. `docker compose ps` показывает `board` как `healthy`.

## Решения без ученика

1. Листание не пишется в очередь, вместо этого есть строка курсора. Цена ошибки: тренер не видит, какие позиции ученик просматривал без ходов.
2. Шаг задачи «Верно, продолжайте» не пишется, пишутся ошибка, «слабее», решено и «Показать решение». Цена: тренер не видит промежуточные верные ходы, но они есть в `board state`.
3. Повторный выбор существующего хода пишется как ход ученика. Цена: лишняя строка, если ученик просто листал кликом по доске ходом.
4. Тексты событий собирает сервер, Python только печатает. Цена: текст по-русски живёт в TypeScript; при переносе `coach` на TypeScript (этап 4) это даже удобнее.
5. Очередь хранит 500 событий. Цена: при долгом перерыве без чтения старые события теряются.
6. Хук помечает события прочитанными. Цена: если тренер не обратил внимания на блок в контексте, повторно его не увидит без `board state`.
7. Оценка на шкале со стороны белых, как на Lichess, а не со стороны ученика. Ученику в чате тренер по-прежнему называет оценку с его стороны. Цена: ученик, играющий чёрными, видит минус как свой перевес.
8. Замена дерева выключает всю панель, включая заметку. Цена: тренеру надо заново включать панель после каждой новой позиции.
9. Глубина анализа панели - бюджет узлов сервиса по умолчанию (1 000 000), без постепенного углубления. Цена: оценка в острых позициях менее точна, чем у `coach analyze`.
10. Подключение WebSocket без `Origin` разрешено. Цена: локальная программа на машине ученика может управлять доской; так было и раньше, сервер слушает только `127.0.0.1`.
11. Валидаторы руками, без `class-validator`. Цена: чуть больше кода, зато без новой зависимости и декораторов в общих типах.
